# 数据库设计说明书

版本：v1.0
日期：2026-08-15
配套方案：`政府采购信息采集与销售提醒系统-设计方案.md`（v1.1）

---

## 1. 设计目标与原则

1. **幂等去重**：同一公告无论被采集多少次，只存一行（唯一约束兜底）；
2. **一公告一明细多**：一份意向公开公告可含多条采购项目，必须拆表；
3. **标签驱动分析**：所有可分析维度（区域/类型/金额区间/时间/项目阶段）在入库时打成标签，后续统计直接按标签聚合，无需回源解析；
4. **溯源保底**：每条记录保留源接口原始 JSON（raw_json），源站改版或解析出错时可恢复；
5. **项目级串联预留**：公告 → 项目（意向→招标→中标→合同全链路）的关系在表结构中预留，二期启用；
6. **扩展友好**：数据源只做上海站，但 site_code 字段从第一天就存在，未来加站点零成本。

## 2. ER 关系总览

```
                          ┌─────────────────────────────┐
                          │       projects (项目表)      │
                          │  id / project_code (唯一)     │
                          │  project_name / purchaser    │
                          └──────────────┬──────────────┘
                                         │ 1
                                         │
                                         │ N（一个项目多份公告）
                                         ▼
   ┌─────────────────────────────────────────────────────────────┐
   │                  announcements (公告主表)                     │
   │  id (PK) │ (site_code, article_id) 唯一 │ type │ title │      │
   │  purchaser │ district │ publish_time │ project_code │ tags  │
   └───────┬──────────────────────────┬─────────────────────────┘
           │ 1                        │ 1
           │ N（一份意向→多条明细）       │ N（一条公告→多条人工标签）
           ▼                          ▼
   ┌──────────────────────┐   ┌──────────────────────────┐
   │ intention_items      │   │ announcement_tags        │
   │ (意向明细表)           │   │ (人工标签表)              │
   │ announcement_id (FK) │   │ announcement_id (FK)     │
   │ item_name / budget   │   │ tag_key / tag_value      │
   │ expect_month         │   └──────────────────────────┘
   └──────────────────────┘

   配置表（与公告数据独立，人工维护）：
   ┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐
   │ sales_regions   │   │ daily_digests   │   │ collect_runs    │
   │ (区域-销售清单)   │   │ (日报发送日志)    │   │ (采集任务状态)    │
   └─────────────────┘   └─────────────────┘   └─────────────────┘
```

### 关系说明

| 关系 | 类型 | 说明 |
|---|---|---|
| projects ← announcements | 1:N | 一个项目（project_code）对应多份公告（意向/招标/中标/合同）。一期仅在有 project_code 时写入；意向公告无 project_code，二期用"采购人+项目名称"匹配归并 |
| announcements ← intention_items | 1:N | 一份意向公告含多条采购项目明细 |
| announcements ← announcement_tags | 1:N | 一条公告可打多条人工标签 |

> 数据表（announcements / intention_items）与配置表（sales_regions）**不建外键**——公告的区划是"事实"，销售的区划是"配置"，两者通过 district_name 文本匹配；配置变更不回溯改公告。

## 3. 表结构详解

### 3.1 announcements — 公告主表（核心表）

**用途**：每个栏目（意向/招标/中标）的每条公告一行。列表接口 + 详情接口的数据合并写入。

```sql
CREATE TABLE announcements (
  id               BIGSERIAL PRIMARY KEY,
  -- ── 标识与去重 ──────────────────────────────────────
  site_code        TEXT NOT NULL DEFAULT 'sh-zfcg',   -- 站点；预留多站
  article_id       TEXT NOT NULL,                     -- 源站唯一ID（列表接口）
  -- ── 类型（自动标签的物理列）─────────────────────────
  category_code    TEXT NOT NULL,                     -- 源栏目编码 10016/2/4
  type             TEXT NOT NULL,                     -- intention|bidding|award
  type_detail      TEXT,                              -- 公开招标/竞争性磋商/中标（成交）…
  -- ── 基础信息（列表接口即有）─────────────────────────
  title            TEXT NOT NULL,
  purchaser        TEXT,                              -- 采购人
  publisher        TEXT,                              -- 发布机构
  district_name    TEXT,                              -- 区划名称
  district_code    TEXT,                              -- 区划编码
  publish_time     TIMESTAMPTZ NOT NULL,              -- 发布时间（毫秒转）
  expired_at       TIMESTAMPTZ,                       -- 公告过期时间
  -- ── 项目信息（详情接口）─────────────────────────────
  project_code     TEXT,                              -- 项目编号（招标/中标有）
  project_name     TEXT,                              -- 项目名称
  bid_open_time    TIMESTAMPTZ,                       -- 开标时间（招标正文解析）
  fund_source      TEXT,                              -- 资金性质：国库/自筹/混合
  budget_amount    NUMERIC(18,2),                     -- 预算金额（招标正文）
  award_amount     NUMERIC(18,2),                     -- 成交金额（中标正文）
  supplier         TEXT,                              -- 中标供应商（正文有则填，附件PDF二期解析）
  -- ── 正文与附件 ────────────────────────────────────
  content_html     TEXT,                              -- 正文HTML（详情接口）
  content_text     TEXT,                              -- 正文纯文本（检索/关键词匹配）
  attachment_info  JSONB,                             -- 附件清单 [{name,url}]
  track_links      JSONB,                             -- 项目时间线 announcementLinkDtoList
  -- ── 标签与溯源 ────────────────────────────────────
  tags             JSONB NOT NULL DEFAULT '{}',       -- 自动+人工标签（见§4）
  raw_json         JSONB,                             -- 列表/详情原始返回（溯源）
  -- ── 处理状态 ─────────────────────────────────────
  detail_status    TEXT NOT NULL DEFAULT 'pending',   -- pending|done|failed
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),

  UNIQUE (site_code, article_id)                      -- 幂等去重核心
);
```

**索引**：

```sql
CREATE INDEX idx_ann_type      ON announcements (type);
CREATE INDEX idx_ann_time      ON announcements (publish_time);
CREATE INDEX idx_ann_district  ON announcements (district_name);
CREATE INDEX idx_ann_project   ON announcements (project_code);
CREATE INDEX idx_ann_purchaser ON announcements (purchaser);
CREATE INDEX idx_ann_tags      ON announcements USING GIN (tags);   -- 标签组合查询
CREATE INDEX idx_ann_status    ON announcements (detail_status) WHERE detail_status = 'pending';  -- 详情重试队列
```

### 3.2 intention_items — 意向明细表

**用途**：一份意向公开公告的正文表格里常有**多条采购项目**（"序号 | 采购项目名称 | 采购需求概况 | 预算金额 | 预计采购时间 | 备注"），逐条拆开存，才能按"项目"和"金额"分析。

```sql
CREATE TABLE intention_items (
  id              BIGSERIAL PRIMARY KEY,
  announcement_id BIGINT NOT NULL REFERENCES announcements(id) ON DELETE CASCADE,
  seq_no          INT,                        -- 表格序号
  item_name       TEXT NOT NULL,              -- 采购项目名称
  item_summary    TEXT,                       -- 采购需求概况
  budget_amount   NUMERIC(18,2),              -- 预算金额（元）
  expect_month    TEXT,                       -- 预计采购时间（2026-09）
  remark          TEXT,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_intent_ann   ON intention_items (announcement_id);
CREATE INDEX idx_intent_name  ON intention_items (item_name);
```

**为什么拆表而不塞进 announcements**：
- 一条意向公告 = N 条商机，不拆开就没法按"单个采购项目"匹配销售产品线；
- 金额是明细级的（172.6万是"集成电路测试设备"的预算，不是整份公告的）。

### 3.3 projects — 项目表（二期启用，一期建结构）

**用途**：跨公告串联同一个采购项目（意向→招标→中标→合同），支撑"项目全生命周期"分析。

```sql
CREATE TABLE projects (
  id           BIGSERIAL PRIMARY KEY,
  project_code TEXT NOT NULL,                  -- 项目编号
  project_name TEXT,
  purchaser    TEXT,                           -- 采购人（归并锚点之一）
  first_seen   TIMESTAMPTZ NOT NULL DEFAULT now(),  -- 首次出现在我们数据里（意向时点）
  last_seen    TIMESTAMPTZ,
  stage        TEXT NOT NULL DEFAULT 'intention',    -- 最新阶段：intention|bidding|award|contract
  budget_amount NUMERIC(18,2),                 -- 归并后的预算（招标为准）
  award_amount  NUMERIC(18,2),                 -- 归并后的成交金额
  winner        TEXT,                          -- 归并后的中标供应商
  tags          JSONB DEFAULT '{}',            -- 项目级标签（产品线等）
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (project_code)
);
```

**一期策略**：有 project_code 的招标/中标公告写入 projects（upsert），意向公告暂不建项目行；二期用"采购人 + 项目名称"把意向归并进同一项目，形成完整时间线。

### 3.4 sales_regions — 区域-销售清单（配置表，运营自维护）

**用途**：销售负责哪些区域。管理界面增删改 + CSV 导入导出。日报任务每次运行读最新数据。

```sql
CREATE TABLE sales_regions (
  id           SERIAL PRIMARY KEY,
  sales_name   TEXT NOT NULL,                  -- 销售姓名
  sales_email  TEXT NOT NULL,                  -- 收件邮箱
  region       TEXT NOT NULL,                  -- 区划名称（上海市浦东新区）
  region_code  TEXT,                           -- 区划编码（更精确，可选）
  note         TEXT,                           -- 备注
  is_active    BOOLEAN NOT NULL DEFAULT TRUE,  -- 停用不删，保留历史
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (sales_email, region)                 -- 一人多区：一个销售可有多行
);
```

**设计要点**：
- 一个销售多区域 → 多行（张三：浦东新区 / 徐汇区）；
- 停用用 is_active 而非删除 → 日报历史可追溯；
- 区域文本与公告 district_name 匹配；未匹配进"待分配"池（见 §5）。

### 3.5 daily_digests — 日报发送日志（审计 + 防重发）

**用途**：每次日报每封邮件一行。sent 后不可重复发，失败可定位。

```sql
CREATE TABLE daily_digests (
  id            BIGSERIAL PRIMARY KEY,
  report_date   DATE NOT NULL,                 -- 报表日期（采集窗口日）
  sales_email   TEXT NOT NULL,
  region        TEXT NOT NULL,
  intention_cnt INT DEFAULT 0,                 -- 三类计数
  bidding_cnt   INT DEFAULT 0,
  award_cnt     INT DEFAULT 0,
  sent_at       TIMESTAMPTZ,
  status        TEXT NOT NULL DEFAULT 'pending', -- pending|sent|failed
  error         TEXT,
  UNIQUE (report_date, sales_email, region)    -- 同日同人同区只发一次
);
```

### 3.6 collect_runs — 采集任务状态（监控）

**用途**：每天每次采集一行，记录翻页数、新增数、详情成功数；失败可重跑且可审计。

```sql
CREATE TABLE collect_runs (
  id            BIGSERIAL PRIMARY KEY,
  run_date      DATE NOT NULL,
  site_code     TEXT NOT NULL,
  category      TEXT NOT NULL,                 -- 10016/2/4
  page_count    INT,
  fetched_cnt   INT,                           -- 接口返回条数
  inserted_cnt  INT,                           -- 实际新增入库
  detail_ok_cnt INT,                           -- 详情解析成功数
  status        TEXT NOT NULL,                 -- running|success|failed
  error         TEXT,
  started_at    TIMESTAMPTZ,
  finished_at   TIMESTAMPTZ
);
```

### 3.7 announcement_tags — 人工标签表

**用途**：运营打的业务标签（产品线/客户阶段/优先级/自定义），与自动标签（tags JSONB）分开存，便于审计"谁在什么时候打的"。

```sql
CREATE TABLE announcement_tags (
  id              BIGSERIAL PRIMARY KEY,
  announcement_id BIGINT NOT NULL REFERENCES announcements(id) ON DELETE CASCADE,
  tag_key         TEXT NOT NULL,               -- product_line|customer_stage|priority|custom
  tag_value       TEXT NOT NULL,
  operator        TEXT,                        -- 操作人
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (announcement_id, tag_key, tag_value)
);

CREATE INDEX idx_tag_ann ON announcement_tags (announcement_id);
```

### 3.8 视图 — v_daily_summary（报表聚合底座）

```sql
CREATE VIEW v_daily_summary AS
SELECT
  publish_time::date            AS day,
  district_name,
  type,
  type_detail,
  CASE
    WHEN budget_amount IS NOT NULL AND budget_amount < 500000 THEN '<50万'
    WHEN budget_amount < 2000000 THEN '50-200万'
    WHEN budget_amount < 10000000 THEN '200-1000万'
    ELSE '>1000万'
  END                           AS amount_band,
  count(*)                      AS cnt
FROM announcements
GROUP BY 1,2,3,4,5;
```

> 金额区间也可作为标签（amount_band）写入 tags，两种方式并存：视图按需计算，标签便于预聚合。

## 4. 标签体系在数据库中的落地

### 4.1 自动标签 → announcements.tags（JSONB）

采集/解析时由程序写入，例如：

```json
{
  "type": "award",
  "type_detail": "中标（成交）结果公告",
  "district": "普陀区",
  "purchaser": "上海市公安局普陀分局",
  "year_month": "2026-08",
  "amount_band": "50-200万",
  "has_attachment": false,
  "project_track": "award_only"
}
```

### 4.2 人工标签 → announcement_tags 表

```sql
INSERT INTO announcement_tags (announcement_id, tag_key, tag_value, operator)
VALUES (123, 'product_line', '实验室设备', 'ops_li');
```

### 4.3 查询示例（标签驱动分析）

```sql
-- 普陀区、1000万以上、公开招标（自动标签）
SELECT * FROM announcements
WHERE tags @> '{"district":"普陀区","amount_band":">1000万","type_detail":"公开招标公告"}';

-- 某产品线（人工标签）的意向明细
SELECT a.title, i.item_name, i.budget_amount, i.expect_month
FROM announcements a
JOIN intention_items i ON i.announcement_id = a.id
JOIN announcement_tags t ON t.announcement_id = a.id
WHERE t.tag_key = 'product_line' AND t.tag_value = '实验室设备';

-- 按日×区划×金额区间统计（视图）
SELECT * FROM v_daily_summary WHERE day >= '2026-08-01' ORDER BY day, district_name;
```

## 5. 日报生成的查询路径

```
每天18:00，对每个销售（sales_regions 中 is_active=true 且按 email 分组）：
1. 取该销售所有 region
2. 查当日公告：
   SELECT * FROM announcements
   WHERE publish_time >= '当天00:00' AND publish_time < '次日00:00'
     AND district_name IN (该销售区域列表)
   ORDER BY type, publish_time;
3. 意向公告 → 联表取明细（intention_items）生成"意向"段
4. 未匹配区划（不在任何销售清单）→ 待分配池 → 邮件给管理员
5. 写 daily_digests（防重发），发送邮件，回写 sent/failed
```

## 6. 数据生命周期与维护

| 项 | 策略 |
|---|---|
| 保留期限 | 永久保留（年增约 10~15 万条，<1.5GB/年，成本可忽略） |
| 备份 | 每日 pg_dump 到对象存储，保留 30 天 |
| 更新 | 公告内容基本不变；如源站修改，比对 content hash 后更新（二期） |
| 清理 | 无需清理；如未来量大，先归档 expired_at 超 3 年的 |
| 时区 | 统一存 UTC（timestamptz），展示层转 Asia/Shanghai；publishDate 毫秒时间戳入库时转 |

## 7. 设计决策备忘（为什么这样做）

| 决策 | 理由 |
|---|---|
| 唯一键 (site_code, article_id) | 幂等采集的根基，任何重跑都不产生重复行 |
| 意向明细拆表 | 一份公告 = N 条商机，不拆无法按项目分析 |
| 标签用 JSONB + GIN | 维度多且会增长，加维度不加表；组合查询一条 SQL |
| 人工标签单独表 | 可审计（谁/何时/打了什么），与机器标签职责分离 |
| 配置表与数据表不建外键 | 区域匹配是"事实 vs 配置"的文本关联，配置变更不回溯历史数据 |
| projects 一期建表二期填 | 表结构现在就位，避免二期改表迁移 |
| raw_json 保底 | 源站改版/解析 bug 时可从原始数据恢复重解析 |
| 金额 NUMERIC(18,2) | 避免浮点误差，支持精确统计 |
| 时间全 UTC | 多时区/迁移安全，展示层统一转上海时区 |
