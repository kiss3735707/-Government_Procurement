## ADR-001 采集范围：仅上海市，含三类公告

- **决策**：数据源仅上海市政府采购网（www.zfcg.sh.gov.cn）；采集三类：采购意向公开（`ZcyAnnouncement10016`）、采购公告/招标（`ZcyAnnouncement2`）、中标（成交）结果公告（`ZcyAnnouncement4`）。
- **理由**：用户确认只做上海；招标/磋商纳入是用户明确要求。
- **日期**：2026-08-15

## ADR-002 数据库：PostgreSQL 16（开源，非国产库）

- **决策**：PostgreSQL 16，同机部署；表结构见《数据库设计说明书》。
- **理由**：用户确认无国产化硬性要求；PG 官方支持 x86_64；SQL 设计零改动。
- **迁移预案**：若未来强制国产化 → openGauss/人大金仓（PG 系，SQL 微调 1~2 天）。
- **日期**：2026-08-15

## ADR-003 部署环境：信创服务器（海光/兆芯 x86_64 + Ubuntu）

- **决策**：Ubuntu Server 22.04/24.04，x86_64，可访问外网；systemd 原生部署（不依赖 Docker）。
- **理由**：用户确认；x86_64 用官方 amd64 软件，无 ARM 适配问题；systemd 规避内网拉镜像问题。
- **日期**：2026-08-15

## ADR-004 日期过滤：客户端强制，不依赖接口参数

- **决策**：采集按目标日期过滤必须在客户端做——用 `publishDate` 精确判断，绝不信任接口 `beginDate/endDate`。
- **证据**：实测接口传日期参数仍返回相邻日期记录（查 8-14 混入 8-15）。
- **日期**：2026-08-15

## ADR-005 意向明细拆表（1 公告 : N 明细）

- **决策**：`announcements` 与 `intention_items` 分开；一份意向公告的正文表格逐条拆为明细行（项目名/需求/预算/预计月）。
- **理由**：一份意向含多条商机，拆表才能按"单个项目"匹配与分析。
- **日期**：2026-08-15

## ADR-006 标签双通道

- **决策**：自动标签存 `announcements.tags`（JSONB + GIN 索引）；人工标签存 `announcement_tags` 表（可审计操作人）。
- **理由**：自动标签加维度不加表；人工标签需审计；支持任意维度组合查询。
- **日期**：2026-08-15

## ADR-007 区划归一化字典

- **决策**：销售清单只维护标准区名（16 区 + 本级）；源站两种写法（"浦东新区"/"上海市浦东新区"）及简称统一经 `normalizeDistrict()` 归一到标准名；未知区划返回 null 进"待分配池"。
- **证据**：实测 450 条样本存在双写法，28 种去重名称对应 16 区+本级。
- **日期**：2026-08-15

## ADR-008 中标金额统一语义

- **决策**：`awardAmount` = 明细式表格金额（`中标（成交金额）`列）优先，正文"成交总合同金额"汇总兜底；`awardAmountSource` 标记来源（table/summary）。
- **理由**：两种形态并存（汇总式 2/5、明细式 3/5 抽样），统一语义避免分析口径混乱。
- **日期**：2026-08-15

## ADR-009 采购人兜底策略

- **决策**：`purchaser = purchaseName ?? author`，并记录 `purchaserSource`；二期可从正文"采购人信息"节提取更精确采购人。
- **证据**：中标结果里 `purchaseName` 常为 null，`author`（发布机构）有值。
- **日期**：2026-08-15

## ADR-010 礼貌采集策略

- **决策**：请求间隔 ≥600ms，重试 3 次指数退避（1s/2s/4s），只拉当日增量，UA 标注 Mozilla 兼容、带 Referer。
- **理由**：公开信息低频采集，不冲击源站；robots.txt 被 307 重定向，以自律策略为准。
- **日期**：2026-08-15

## ADR-011 现网库与 jsonb 入库

- **决策**：PostgreSQL 16.15 部署在 `10.12.64.101:5432`，业务库/用户 `zfcg`；本机经 VPN `192.169.0.5` 直连。连接串只放 `.env` 的 `DATABASE_URL`。jsonb 列统一 `JSON.stringify` 后 `$n::jsonb`，避免 node-pg 把对象序列化成非法 JSON。
- **理由**：5432 已对开发 VPN 开放；源站 `announcementLinkDtoList` 直接绑参数曾报 `22P02 invalid input syntax for type json`。
- **日期**：2026-09-18

## ADR-019 二期数据与现网隔离

- **决策**：二期只补历史中标。AI 输出按《Ai自动打标字典》第六章存入 `announcement_ai.payload`，包件拆到 `award_packages`。不建供应商主表，不把 AI 字段写入 `announcements.tags`。模型配置进 `llm_settings`，密钥不进 git。补采失败状态不进入每日 `pending`/`failed` 重试队列。不修改 17:00 采集与 18:00 日报的单元和命令。每日打标用独立 timer（规划 20:00）。智能体接口只读、单独鉴权。

## ADR-020 历史补采的列表时间参数

- **决策**：历史中标补采向 `/portal/category` 传 `publishDateBegin` / `publishDateEnd`（Asia/Shanghai 当日 00:00 至当日 23:59:59.999 的毫秒时间戳）。结束时间不能用次日 00:00，否则接口返回次日。入库前仍用 `publishDate` 做客户端精确过滤。不使用现有 `beginDate`/`endDate` 字符串，也不从第 1 页向历史翻页。
- **证据**：2026-09-28 实测。`beginDate=2024-01-01` 时 `total=75645`，首页全为 2026-09-28。改用毫秒窗口后，2024-01-01 返回 3 条且日期均为当天；窗口跨日时会混入相邻日。
- **理由**：现有按天采集只覆盖最近列表，到不了 2024。ADR-004 的客户端过滤仍然有效。
- **日期**：2026-09-28

## ADR-021 17:00 后公告顺延到次日邮件

- **决策**：每日定时采集（不带 `--date`）先采昨天全天，再采今天到启动时刻。已入库的公告按 `(site_code, article_id)` 跳过。手工 `--date` 仍只采指定的一天。18:00 日报在当天正文之外增加「昨日补入」：发布日是昨天，且 `created_at` 晚于昨天已发送日报的 `sent_at`。昨天没有成功发送记录时不补入。定时器命令不改，仍是 `node src/index.js --no-save` 与 `node src/digest.js run --send`。
- **理由**：17:00 到 24:00 发布的公告赶不上当天 18:00 邮件。次日 17:00 入库后，用发送时间把已经进过昨天邮件的公告排除，避免整封重发。
- **日期**：2026-10-12

## ADR-022 每日新增中标打标先只留在本机

- **决策**：每天 20:00 用 `node src/tag-awards.js --today` 只打上海时区当天、尚未成功也未放弃的中标。定时器文件是 `deploy/zfcg-tag-daily.timer`，不改 17:00 采集和 18:00 日报。模型失败只记在 `announcement_ai`，不发信。历史打标还在服务器上跑，这个定时器先不安装、不启用。
- **理由**：用户要求本机开发和测试，不动服务器配置。每天打标若现在启用，会和历史打标抢同一个模型网关。
- **日期**：2026-10-14

## ADR-023 智能体只读接口本机先实现

- **决策**：业务分析走三个只读 GET：`/api/agent/stats`、`/api/agent/announcements`、`/api/agent/announcements/{id}`。鉴权用 `AGENT_TOKEN`，不用管理界面 cookie。中标汇总金额用 `award_packages.deal_amount`，并且只统计打标成功的包件。供应商名称不归并。历史打标结束前不部署、不重启管理界面。
- **理由**：标签是给智能体做分析用的。汇总在服务端完成，名单和正文分开取，避免一次拉回几万条。打标进程还在占用服务器，接口先在本机测通。
- **日期**：2026-10-21

## ADR-024 打标生成上限改为 8000

- **决策**：中标打标请求的 `max_tokens` 从 2000 改为 8000。模型上下文仍按 50 万 token 理解，这个数字只限制单次生成。连接测试的 `max_tokens: 8` 不改。服务器上的旧程序先不替换，506 条失败记录先不重打。
- **理由**：用户确认模型上下文是 50 万 token。失败公告的 JSON 在大约 5000 字处被 2000 token 的生成上限截断。8000 够写完这些 JSON，同时给正文和提示词留在 50 万上下文里。
- **日期**：2026-10-21

## ADR-025 历史打标结束后启用每天 20:00 打标

- **决策**：`zfcg-tag-daily.timer` 已在服务器启用。每天 20:00 运行 `node src/tag-awards.js --today`，只打上海时区当天、尚未成功也未放弃的中标。不改 17:00 采集和 18:00 日报，不调用发信。
- **理由**：历史打标已结束，失败记录已放弃。生成上限已是 8000。每天打标不再和历史任务抢同一个模型网关。
- **日期**：2026-10-22
