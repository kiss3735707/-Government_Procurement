# 会话恢复协议（Context Recovery Protocol）

> **目标**：任何新会话（新对话/新 agent/新接手人）在**不依赖历史对话**的情况下，5 分钟内进入可工作状态。
> **原理**：把项目记忆放在仓库文件里，而不是上下文里。上下文只做"引导"，文件做"记忆"。

---

## 1. 新会话启动：三步接续法（必读）

```
第 1 步  读 docs/PROGRESS.md          ← 当前状态、下一步、阻塞项（2 分钟）
第 2 步  读 docs/会话恢复协议.md       ← 本文件：接续方法与验证命令（2 分钟）
第 3 步  读 docs/决策日志.md           ← 已定决策，避免重谈/推翻（1 分钟）
然后     按 PROGRESS.md §5 的下一步清单开始工作
```

> 规则：**工作前先读这三份文件**。不要凭对话印象猜项目状态。

## 2. 会话结束：四步收尾（必做）

每次会话结束（或阶段完成）时，必须更新并提交：

```
1. 更新 docs/PROGRESS.md
   - §2 当前状态（阶段/阻塞项/最近验证）
   - §5 下一步清单（勾掉完成的，写清下一步）
2. 若做了新决策 → 追加 docs/决策日志.md
3. 若改了架构/接口 → 同步相关设计文档
4. git add docs/ && git commit -m "docs: 进度更新（<阶段>）"
```

## 3. 验证命令（确认系统状态）

```bash

cd <项目根目录>

node src/index.js --date 2026-09-17 --limit 2
```

## 4. 关键约定（新会话必须遵守，防踩坑）

| 约定 | 说明 | 来源 |
|---|---|---|
| 日期过滤 | **客户端按 publishDate 精确过滤**，绝不依赖接口 beginDate/endDate（实测不可靠，混入相邻日期） | M1 校准 §3.1 |
| 区划匹配 | 用 `normalizeDistrict()` 归一化后再匹配销售清单；未知区划进"待分配池" | M1 校准 §3.2 |
| 中标金额 | `awardAmount` 统一语义：明细式表格优先，汇总式兜底 | M1 校准 §3.3 |
| 采购人 | 中标结果 purchaseName 常为 null，用 author 兜底 + purchaserSource 标记 | M1 校准 §3.4 |
| 礼貌策略 | 请求间隔 ≥600ms；重试 3 次指数退避；只拉当日增量 | 方案 §6 |
| 时区 | 时间统一存 UTC（timestamptz），展示转 Asia/Shanghai | DB 设计 §6 |
| 凭据 | SMTP/DB 配置走环境变量或 .env（已 gitignore），绝不入库 | .gitignore |
| 代码 | Node ESM（type: module），Node ≥20 | package.json |

## 5. 常见问答（新会话可能疑惑的）

**Q: 为什么要拆 intention_items 表？**
A: 一份意向公告含 N 条采购项目明细（各带独立预算/预计月），拆表才能按"单个商机"分析。

**Q: 标签为什么双通道？**
A: 自动标签（JSONB+GIN）程序打、加维度不加表；人工标签（独立表）运营打、可审计"谁何时打的"。

**Q: 为什么不用接口的日期参数？**
A: 实测 `beginDate/endDate` 返回数据混入相邻日期记录，语义不可靠，必须客户端过滤。

**Q: M2 的 upsert 主键？**
A: `(site_code, article_id)` 唯一约束 + `ON CONFLICT DO NOTHING`。
