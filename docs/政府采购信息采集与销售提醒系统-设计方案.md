# 政府采购信息采集与销售提醒系统 — 设计方案

版本：v1.1（方案稿，未实现）
日期：2026-08-15
范围：**仅上海市**（www.zfcg.sh.gov.cn，政采云平台）
本文档基于 2026-08-15 实机接口验证，所有接口与字段均经真实调用确认。

---

## 1. 项目背景与目标

### 1.1 背景
销售团队需要第一时间掌握上海市政府采购动向：
- **采购意向公开**：采购人提前公示未来采购计划（含预算金额），是销售"提前介入"的最佳窗口期；
- **采购公告（招标/磋商等）**：项目正式启动，销售需评估是否投标；
- **中标（成交）结果公告**：谁中了标、金额多少，用于竞争情报与复盘。

信息目前靠人工浏览网站，滞后且易漏。需要一个自动采集 + 定向分发的系统。

### 1.2 目标
1. **每天 17:00 自动采集**当日新增的三类公告（意向公开、采购公告、中标结果），入库；
2. **自动按行政区域匹配销售负责人**，每天定时把"新增意向、新开招标、新出中标"汇总邮件发给对应销售；
3. **数据落库并带多维标签**，支撑后续从不同维度（区域、采购人、项目、金额、时间、类型…）统计分析。

### 1.3 成功标准（可度量）
- 采集延迟：公告发布后 ≤24 小时入库（每日 17:00 任务，覆盖当日全天新增）；
- 数据准确率：标题/采购人/区划/发布日期解析准确率 ≥99%；
- 去重率：同一公告重复入库率 0（以公告唯一 ID 去重）；
- 邮件到达：销售邮箱送达成功 ≥99%，无重复发送；
- 分析可用：入库数据可直接按任意标签维度聚合查询，无需二次清洗。

## 2. 需求分析

### 2.1 功能需求

| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 定时采集 | 每天 17:00 触发，抓取当日新增公告（意向公开 + 采购公告 + 中标结果） |
| F2 | 详情抓取 | 列表入库后异步抓取详情：正文、金额、项目编号、供应商、附件等 |
| F3 | 增量与去重 | 按公告唯一 ID 增量入库，天然幂等 |
| F4 | 数据归一化 | 解析出结构化字段 + 多维标签 |
| F5 | 区域匹配 | 公告区划 → 销售负责人（自维护清单） |
| F6 | 邮件分发 | 每个销售收到**自己区域**的当日汇总邮件 |
| F7 | 日报分类 | 邮件内按"意向公开 / 招标中 / 中标结果"三类呈现 |
| F8 | 清单自维护 | 区域-销售清单支持运营自行添加/删除（管理界面或 CSV 导入导出） |
| F9 | 数据查询 | 按任意标签维度查询（区域/时间/类型/关键词/采购人/金额区间） |
| F10 | 运维监控 | 采集失败、邮件失败可告警；任务有日志 |

### 2.2 非功能需求

| 类别 | 要求 |
|---|---|
| 可靠性 | 单次任务失败可重试，不丢数据；采集与发送解耦 |
| 时效 | 17:00 任务开始后 60 分钟内完成采集+详情+发送 |
| 合规 | 仅采集政府依法公开的信息；控制请求频率，不冲击源站；邮件仅发内部员工 |
| 成本 | 单台云服务器承载（采集+DB+邮件+管理界面），日增约 200~500 条 |
| 可扩展 | 标签体系开放；数据源适配器预留（本方案仅上海站） |

### 2.3 用户角色
- **销售**：每天收邮件，看本区域新增意向/招标/中标；
- **运营/销售管理**：维护"区域-销售"清单（自增删）、看全量数据；
- **管理者/分析**：用多维标签做统计分析；
- **系统管理员**：部署、监控、处理失败任务。

```

正文含：成交总合同数、成交总合同金额（元）

```

## 4. 重要数据识别与标签体系设计（重点）

### 4.1 重要数据字段（按分析价值排序）

| 优先级 | 字段 | 来源 | 分析价值 |
|---|---|---|---|
| ★★★ | 预算金额 | 意向明细/招标正文 | 商机规模、市场容量 |
| ★★★ | 采购人（purchaseName） | 列表 | 客户画像、复购分析 |
| ★★★ | 区划（districtName） | 列表 | 区域维度、销售归属 |
| ★★★ | 采购项目名称（明细级） | 意向正文 | 产品线匹配、关键词订阅 |
| ★★★ | 中标供应商 + 成交金额 | 中标正文/附件 | 竞争情报、市场份额 |
| ★★☆ | 项目编号 projectCode | 详情 | 项目级关联（意向→招标→中标全链路） |
| ★★☆ | 预计采购时间（月） | 意向正文 | 销售跟进排期 |
| ★★☆ | 开标时间 | 招标正文 | 投标时效提醒 |
| ★★☆ | 发布时间 | 列表 | 时效分析、发布规律 |
| ★☆☆ | 附件（招标文件/明细PDF） | 详情 | 深度尽调 |
| ★☆☆ | 点击量 | 详情 | 热度参考 |
| ★☆☆ | 资金性质（国库/自筹） | 招标正文 | 资金结构分析 |

### 4.2 多标签体系设计（预留多维度统计）

> 设计原则：**公告入库即打标签**，标签全部落库为可查询维度；后续分析/报表直接按标签聚合，无需回源。

**A. 系统自动标签（采集时打，无需人工）**

| 标签维度 | 取值示例 | 打标来源 |
|---|---|---|
| `type` 公告类型 | intention / bidding / award | 栏目编码 |
| `type_detail` 细分类 | 公开招标/竞争性磋商/单一来源/询价/中标（成交）… | pathName + categoryNames |
| `district` 区划 | 上海市本级/浦东新区/普陀区… | districtName |
| `purchaser` 采购人 | 上海理工大学/上海市公安局… | purchaseName |
| `year_month` 发布月 | 2026-08 | publishDate |
| `intent_month` 预计采购月 | 2026-09（意向公开） | 正文解析 |
| `amount_band` 金额区间 | <50万 / 50-200万 / 200-1000万 / >1000万 | 预算/成交金额映射 |
| `fund_source` 资金性质 | 国库/自筹/混合 | 招标正文 |
| `has_attachment` 有无附件 | true/false | attachmentVO |
| `project_track` 项目阶段 | 仅意向 / 意向→招标 / 招标→中标 / 全链路 | announcementLinkDtoList |

**B. 人工标签（运营可维护，用于业务侧分组）**

| 标签维度 | 说明 |
|---|---|
| `sales_owner` 销售归属 | 由区域-销售清单自动推导，可人工覆盖 |
| `product_line` 产品线 | 运营按关键词/项目名打（如"实验室设备"、"信息化"） |
| `customer_stage` 客户阶段 | 运营打（潜在/跟进中/已投标/已中标） |
| `priority` 优先级 | 运营打（高/中/低） |
| `custom_tag` 自定义 | 自由文本标签，任意维度 |

**C. 实现方式**
- 系统标签：采集/解析时写入 `announcements.tags JSONB` + 独立索引列（见 §7）；
- 人工标签：管理界面维护 `announcement_tags` 表（公告ID + tag_key + tag_value + 操作人 + 时间）；
- 查询：任何标签组合都可 SQL 聚合（如 `WHERE tags->>'district'='普陀区' AND tags->>'amount_band'='>1000万' GROUP BY type_detail`）。

## 6. 数据采集模块设计

### 6.1 调度策略
- **采集任务**：每天 17:00；
  - 窗口：抓取 `[当天 00:00, 当天 17:00)` 新增（上线时按实际发布规律校准）；
  - 可选补采：09:00 加一次"补前一晚"（部署后按数据量决定）。
- **日报任务**：每天 18:00（采集+详情完成后，留缓冲；未完成则等待/告警）。

### 6.2 采集流程（幂等）
```
1. 对每个栏目（10016 / 2 / 4）：
   a. 计算采集窗口
   b. 分页请求 /portal/category（pageNo 递增，pageSize=50 建议）
   c. 每页 → 以 articleId 去重入库（DB 唯一约束兜底）
   d. 停止：本页最早 publishDate < 窗口起点 或 空页
   e. 记录 collect_runs 状态
2. 列表入库后，对新增公告异步抓详情（队列+重试，见 6.3）
3. 全程限速：每请求 ≥500ms；失败指数退避重试 3 次
4. 单栏目失败不阻塞其他；整站失败告警
```

### 6.3 详情抓取与重试
- 详情接口：`GET /portal/detail?articleId=<id>&parentId=137027`（siteId=77 经 getSiteId 获取，缓存）；
- 新增公告 → 进入详情队列 → 逐个抓取 → 解析 → 更新公告行 + 写入意向明细/项目信息；
- 失败重试 3 次（退避）；仍失败标记 `detail_status=failed`，次日任务重试；
- **速率控制**：日新增约 200~500 条，间隔 500ms → 约 4 分钟完成，无压力。

### 6.4 去重与增量
- 主键：`(site_code, article_id)` 唯一约束，`ON CONFLICT DO NOTHING`；
- 更新策略：公告内容基本不变；如源站修改，比对 content hash 更新（二期）。

## 7. 数据存储设计

> **完整数据库设计见独立文档《[数据库设计说明书.md](数据库设计说明书.md)》（ER 图、每张表字段注释、索引、标签落库、查询示例、设计决策）。** 本节为摘要。

### 7.1 表结构概览（PostgreSQL 16）

| 表 | 用途 | 关键点 |
|---|---|---|
| `announcements` | 公告主表（意向/招标/中标各一行） | 唯一键 `(site_code, article_id)` 幂等去重；`tags JSONB` 自动标签；`raw_json` 溯源保底 |
| `intention_items` | 意向明细表（1 公告 : N 明细） | 拆出每个采购项目的名称/需求/预算/预计采购月 |
| `projects` | 项目表（二期启用，一期建结构） | `project_code` 串联意向→招标→中标→合同 |
| `sales_regions` | 区域-销售清单（运营自维护） | 一人多区多行；is_active 停用不删 |
| `daily_digests` | 日报发送日志 | 防重发：`UNIQUE(report_date, sales_email, region)` |
| `collect_runs` | 采集任务状态 | 监控/审计/失败重跑 |
| `announcement_tags` | 人工标签（产品线/阶段/优先级） | 可审计操作人 |
| `v_daily_summary` | 聚合视图 | 按日×区划×类型×金额区间预聚合 |

### 7.1.1 表结构（PostgreSQL 16）

**表 1：announcements（公告主表，一公告一行）**
```sql
CREATE TABLE announcements (
  id               BIGSERIAL PRIMARY KEY,
  site_code        TEXT NOT NULL DEFAULT 'sh-zfcg',
  article_id       TEXT NOT NULL,
  category_code    TEXT NOT NULL,          -- 10016 / 2 / 4
  type             TEXT NOT NULL,          -- intention | bidding | award
  type_detail      TEXT,                   -- 公开招标/竞争性磋商/中标（成交）…
  title            TEXT NOT NULL,
  purchaser        TEXT,                   -- 采购人
  publisher        TEXT,                   -- 发布机构
  district_name    TEXT,
  district_code    TEXT,
  publish_time     TIMESTAMPTZ NOT NULL,
  expired_at       TIMESTAMPTZ,
  project_code     TEXT,                   -- 项目编号（招标/中标）
  project_name     TEXT,                   -- 项目名称
  budget_amount    NUMERIC(18,2),          -- 预算金额（招标正文）
  award_amount     NUMERIC(18,2),          -- 成交金额（中标正文）
  supplier         TEXT,                   -- 中标供应商（可空，明细在附件时为空）
  content_html     TEXT,                   -- 正文 HTML
  content_text     TEXT,                   -- 正文纯文本（检索用）

## 8. 区域-销售清单与日报

### 8.1 清单自维护（F8，你要求的"自己添加删除"）
- **管理界面**（推荐）：Web 页面提供表格增删改（销售姓名/邮箱/区域/备注/启用），保存即生效；
- **CSV 导入导出**：界面支持批量导入/导出 CSV（模板：sales_name,sales_email,region,region_code,note,is_active），方便你后续一次性导入初版清单；
- **生效机制**：日报任务每次运行时读表（不缓存），清单改动当日生效；
- **未匹配处理**：公告区划不在清单中 → 进入"待分配"池（不匹配任何销售区域日报），避免静默丢失；
- **管理员全市日报**：`DIGEST_ADMIN_EMAIL` 每日一封「全市」日报，含当日全部公告；若该邮箱与某销售相同，则不再另发其区域信（避免重复）。
- **一人多区**：一个销售可配置多个区域（UNIQUE 允许），一封邮件汇总其所有区域。

### 8.2 日报邮件内容结构（每个销售一封）
```

     预算约 172.6 万元 | 预计采购 2026-09 | 采购人：上海理工大学 [链接]
  2. ...

  1. [生物信息学计算与GPU服务器的公开招标公告]

### 8.3 邮件规则
- 分组发送：每个销售一封，只含自己区域；
- 空区域不发或发"今日无新增"简讯（开关）；
- 附件：CSV 导出当日明细（可选，方便销售导入 CRM）；
- 重试 3 次 + 防重发（daily_digests 唯一约束）。

## 10. 部署环境与服务器配置（信创）

### 10.1 已确认的信创环境

| 项 | 确认值 | 影响 |
|---|---|---|
| CPU 架构 | **海光/兆芯（x86_64）** | 所有软件用标准 amd64 官方版即可，**无需 ARM 适配** |
| 操作系统 | **Ubuntu Server 22.04/24.04 LTS** | apt 直接安装，软件生态最全 |
| 网络 | **能访问外网** | 采集任务可直接访问源站；软件包在线安装 |
| 数据库 | **无国产化硬性要求，开源即可** | **PostgreSQL 16**，SQL 设计零改动 |

> 结论：本环境信创约束很轻——x86_64 + Ubuntu + 外网可达，等于标准 Linux 服务器，全部用官方软件，不需要任何特殊适配。备选（如未来强制国产化）：openGauss/人大金仓（PG 系，SQL 微调即可，见 §10.4）。

### 10.2 软件栈清单（全部官方标准版）

| 软件 | 版本 | 安装方式（x86_64/amd64） |
|---|---|---|
| Ubuntu Server | 22.04 或 24.04 LTS | 官方 ISO |
| PostgreSQL | 16 | `apt install postgresql-16`（PGDG 源） |
| Node.js | 20 LTS（或 Python 3.11） | 官方 tarball / nvm / apt |
| 邮件 | 公司 SMTP（待提供） | 无需安装 |

### 10.3 服务器配置建议

| 项 | 建议 |
|---|---|
| CPU | 2 核（x86_64） |
| 内存 | 4 GB |
| 磁盘 | 系统盘 40GB + 数据盘 100GB（年增 <2GB，宽裕） |
| 带宽 | 5 Mbps 起（采集/邮件均小流量） |
| 数据库 | 同机 PostgreSQL 16（数据量小，无需独立实例） |
| 说明 | 轻量定时任务负载，2C4G 余量很大；未来加 Web 管理界面/报表也够用 |

### 10.4 未来强制国产化时的迁移路径（备选预案）

| 触发条件 | 动作 | 成本 |
|---|---|---|
| 要求国产数据库 | PostgreSQL 16 → openGauss（开源）/ 人大金仓（授权） | 两者均兼容 PG 协议与 JSONB，SQL 微调（如索引语法、时间函数），预计 1~2 天 |
| 要求国产 OS | Ubuntu → 银河麒麟 V10 / 统信 UOS | 均为 Debian 系，命令与 apt 通用，软件包基本复用 |
| 要求国产芯片 | 海光/兆芯（已是国产 x86）→ 无需迁移 | — |

> 设计上已规避迁移雷区：只用标准 SQL + JSONB，不依赖 PG 私有扩展插件，因此无论未来换 openGauss 还是金仓，迁移都只涉及 SQL 微调，不动表结构设计。
